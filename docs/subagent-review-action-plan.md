# Subagent Review Action Plan

This document consolidates the multi-agent review performed on 2026-06-06.
It is intended to guide the next implementation turns after
`docs/expert-roadmap-todo.md`.

## Framing

Pass Lens is strongest today as:

- a trace schema and validator;
- a VS Code workbench for pass-pipeline evidence;
- a repro and agent-context packaging layer;
- a reference MLIR collector scaffold.

The next phase should not prioritize generic AI chat or broad UI expansion.
The review consensus is that credibility depends on:

- real downstream structured collector evidence;
- correct failure attribution;
- large-trace first-screen performance;
- safe artifact path handling;
- a lower-friction open-source release path.

## Priority Order

### P0: Artifact Path Containment

Status:

- [x] Implemented shared containment resolver for artifact paths.
- [x] Reused it in artifact hydration, trace size accounting, webview artifact
  open, and directory repro bundle artifact copying.
- [x] Added focused tests for legal relative paths, absolute path rejection,
  path traversal rejection, and repro bundle copy containment.

Risk:

- Trace files and webview messages can currently reference artifact paths that
  resolve outside the trace directory.
- This affects artifact opening, selected-stage hydration, and directory repro
  bundle copying.

Why this matters:

- Pass Lens is intended to open traces from external users and CI artifacts.
- Artifact paths are evidence, but they should not become arbitrary local file
  access.

Minimum implementation:

- Add one shared resolver such as `resolveArtifactPathWithinTraceRoot()`.
- Default policy:
  - relative paths must remain inside the trace directory;
  - absolute paths are rejected unless an explicit trusted mode is introduced
    later;
  - path traversal such as `../secret.txt` is rejected;
  - diagnostics should report the rejected field and stage.
- Reuse the resolver in:
  - webview artifact open;
  - artifact hydration;
  - directory repro bundle export.

Acceptance checks:

- Unit tests reject absolute paths and escaping relative paths.
- Existing sample artifacts still hydrate.
- `npm test` passes.
- `npm run validate:trace:all` passes.

Suggested files:

- `src/trace/artifactPaths.ts` or `src/trace/artifacts.ts`
- `src/extension.ts`
- `src/directoryReproBundle.ts`
- `tests/trace-artifacts.test.js`
- `tests/directory-repro-bundle.test.js`

### P1: Structured Collector Failure Taxonomy

Risk:

- The structured MLIR collector may conflate `pass_failed` and
  `verifier_failed`.
- This weakens the most important user claim: Pass Lens finds the first bad
  pass or first legality break.

Why this matters:

- Compiler debugging distinguishes pass execution failure from verifier failure
  after a pass.
- Wrong failure attribution will mislead issue summaries, repro bundles, and
  agent exports.

Minimum implementation:

- Audit the MLIR `PassInstrumentation` hooks available to the collector.
- Emit `status: "verifier_failed"` only when the failure is known to be a
  verifier failure.
- Emit `status: "pass_failed"` for pass execution failures.
- Preserve `verifier: "failed"` as supporting evidence, not as a replacement
  for `status`.

Acceptance checks:

- Add a golden verifier-failure trace generated by the collector or a focused
  collector unit test.
- Trace quality and first-signal logic identify the verifier failure correctly.
- `npm test` passes.
- If available on L20, rebuild and smoke-test `pass-lens-mlir-opt`.

Suggested files:

- `collectors/mlir-pass-lens/include/PassLens/PassLensInstrumentation.h`
- `collectors/mlir-pass-lens/lib/PassLensInstrumentation.cpp`
- `docs/mlir-collector-sdk.md`
- `tests/trace-quality.test.js`
- collector smoke scripts or docs under `scripts/`

### P1: Raw Collector Self-Description

Risk:

- Public samples include useful top-level fields such as `provenance`,
  `command`, and capture metadata, but the raw collector path does not clearly
  guarantee it emits all of them.

Why this matters:

- Open-source users will trust a real collector more when the output is
  self-describing and reproducible.
- A sample should not look more complete than the raw collector contract.

Minimum implementation:

- Extend collector options/output to include:
  - provenance kind and description;
  - command line;
  - compiler name/version when available;
  - target/backend when available;
  - process exit code and top-level diagnostics when available.
- Document which fields are collector-owned and which are wrapper-owned.

Acceptance checks:

- A raw collector-generated trace validates with strict schema.
- Sample provenance docs state whether a sample is raw collector output or
  wrapper-augmented output.
- `npm run validate:trace:all` passes.

Suggested files:

- `collectors/mlir-pass-lens/*`
- `docs/collector-author-guide.md`
- `docs/sample-provenance.md`
- `sample-traces/mlir-live-pass-instrumentation.json`

Status: implemented.

### P1: Large Trace First-Screen Performance

Risk:

- Artifact lazy loading avoids reading full IR bodies, but opening a trace can
  still perform many artifact `stat` calls.
- The webview currently receives the whole trace payload at startup, so
  virtualization reduces DOM cost but not JSON payload or parse cost.

Why this matters:

- Real compiler pipelines can produce thousands of stages, many artifacts, and
  large diagnostics.

Minimum implementation:

- Move full artifact-size scanning out of the critical open path.
- Initial trace open should compute only cheap summary data:
  - stage count;
  - inline IR bytes;
  - diagnostics bytes;
  - whether artifact references exist.
- Defer artifact byte totals and largest artifact to a background request or a
  user-triggered trace size report.

Acceptance checks:

- Existing trace size tests still pass.
- Add a test proving open-summary mode does not `stat` every artifact.
- `npm run smoke:large-trace` still passes.

Suggested files:

- `src/trace/size.ts`
- `src/extension.ts`
- `tests/trace-size.test.js`
- `scripts/large-trace-smoke.js`

### P2: Webview Compute Bounds

Risk:

- Timeline virtualization bounds DOM nodes, but several interactions still scan
  all stages or all anomalies.

Why this matters:

- Keyboard navigation, filter changes, and stage selection can become sluggish
  on large traces even when rendering is virtualized.

Minimum implementation:

- Build `anomaliesByStage`.
- Memoize visible stage entries for the current filter/search state.
- Precompute slowest stage and failure indexes.
- Avoid recomputing full lists on every selection move.

Acceptance checks:

- Existing webview tests pass.
- Add a large in-memory webview smoke asserting bounded timeline HTML and cached
  anomaly lookup behavior.

Suggested files:

- `media/tracePanel.js`
- `tests/trace-panel-bounded-diff.test.js`

### P3: Schema Extensibility Lane

Risk:

- Schema v1 is strict and pass-oriented.
- It may be too narrow for LLVM optimization remarks, analysis passes,
  multi-IR boundaries, binary artifacts, and backend-specific evidence.

Why this matters:

- Pass Lens wants to be compiler-agnostic, not only MLIR pass snapshots.

Minimum implementation:

- Design before changing schema behavior.
- Candidate additions:
  - `stage.kind`;
  - artifact `mediaType`;
  - artifact `format`;
  - namespaced `extensions`;
  - optional pipeline boundary metadata.

Acceptance checks:

- Existing v1 examples remain valid.
- New schema examples demonstrate LLVM/remarks or multi-IR evidence.
- Strict validation behavior is documented.

Suggested files:

- `docs/pass-lens.schema.json`
- `src/types.ts`
- `src/trace/strictValidation.ts`
- `docs/schema-examples.md`
- `docs/schema-examples/*`

### P3: Shared Human/Agent Tool Registry

Risk:

- Human QuickPick commands and agent tool manifest are maintained separately.
- Query/report/export capabilities can drift.

Why this matters:

- Pass Lens positions agent integration as deterministic and evidence-grounded.
  The human UI and agent contract should expose the same underlying tool model.

Minimum implementation:

- Create a shared registry for query/report/export definitions.
- Generate QuickPick items and agent tool manifest entries from that registry
  where possible.

Acceptance checks:

- Existing agent tool tests pass.
- Add a test that selected human-visible query/report IDs are present in the
  agent manifest.

Suggested files:

- `src/agentToolManifest.ts`
- `src/traceQuery.ts`
- `src/extension.ts`
- `tests/agent-tool-manifest.test.js`

## Notes For Future Turns

- Keep each turn small and verifiable.
- Prefer focused tests over broad rewrites.
- Do not mark downstream credibility complete until a raw structured trace from
  a real downstream compiler validates with artifact checks.
- Do not strengthen README claims beyond the evidence in `sample-traces/` and
  case-study docs.
- Treat AI features as consumers of deterministic trace evidence, not as the
  product center.
